# 出口 IP 与 VPN

## 1. 一个容易忽略的坑：Go 不认系统代理

这是本项目实际踩到的：**用户的 VPN 是「系统代理」模式（没有 TUN 网卡）**，
Windows 里配了 `127.0.0.1:7897`。结果：

| 路径 | 是否走 VPN |
| --- | --- |
| Chrome / Electron 浏览器通道 | ✅ 认系统代理 |
| **Go 的 net/http 直连请求** | ❌ **不认** |

Go 标准库只在显式配置或 `HTTP_PROXY` 环境变量下才用代理，
**不会去读 Windows 的 Internet 设置**。

后果是同一个程序里两条路径走出两个国家：

```
提交生成（浏览器通道）→ 美国
查积分（Go 直连）    → 中国
```

这个不对称本身就是异常信号，而且用户会觉得「我明明开了 VPN」。

### 修复

`internal/sysproxy` 会读系统代理设置，Go 侧的直连请求按下面的优先级选出口：

```
账号专属代理  >  系统代理  >  直连
```

- Windows：读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`
- 其他平台：读 `HTTPS_PROXY` / `ALL_PROXY` 等环境变量
- 结果缓存 30 秒（换节点后最多半分钟生效）

想强制直连（排查代理问题时）设 `MANAGER_IGNORE_SYSTEM_PROXY=true`。

## 2. 出口体检

```bash
manager netcheck            # 体检当前账号
manager netcheck <账号名>   # 体检指定账号
```

界面上也有（账号详情页）。它会告诉你：

```
  账号        Dreamina-US-主力
  平台归属地  US
  出口代理    http://127.0.0.1:7897（跟随系统代理 / VPN）

  出口 IP     51.81.168.58
  出口地区    US

  ✅ 出口在 US，与账号归属地一致，正常
```

不一致时会明确指出来，并给出建议。

---

## 3. 换节点会怎样

**账号的归属地在注册时就定死了**（存在 `store-idc` / `store-country-code` 里），
换 VPN 节点**不会改变它**。但平台会看请求从哪来：

| 换法 | 结果 |
| --- | --- |
| 同国家换节点（US A → US B） | 一般没事，但同国不同 IP 段仍可能触发验证 |
| **换到别的国家**（US → JP） | **大概率出问题**——轻则报无权限，重则 sessionid 失效 |
| 频繁来回切 | 风险累积，可能被判定异常 |

所以：**一个账号尽量固定一个国家的出口**。

### 建议做法

1. 给每个账号配一个**归属地匹配的专属代理**（界面上可配）
2. 用 `netcheck` 确认出口和归属地一致
3. 换节点之后重新 `netcheck` 一次

专属代理比「全局换 VPN 节点」稳，因为它不会影响其它账号。

## 4. 排查清单

**报 1015 login error**

先跑 `netcheck`。三种可能：

- 出口国家和账号归属地不一致 → 换代理或换节点
- 出口对但集群不对 → 看 [regions.md](regions.md)
- 都对但还是 1015 → 才怀疑 sessionid 真的失效了

**体检说「查不到出口 IP」**

多半是代理只放行部分流量（规则模式），而 IP 查询服务不在放行列表里。
管理器会依次尝试 Cloudflare → ip-api → ipapi → ipinfo，
实测 Cloudflare 在限制最严的节点上也能通。

如果全部失败，说明这个代理基本不可用——那本身就是一个重要信号。

## 5. 一个实测样本

某次真实体检：

```
走系统代理：
  出口 IP   51.81.168.58     出口地区 US     ✅ 一致

  出口 IP   111.45.23.43     出口地区 CN     ⚠️ 不一致
```

同一个账号、同一时刻，两条路径相差一个太平洋。
