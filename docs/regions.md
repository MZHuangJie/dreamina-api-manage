# 多区域支持

## 1. 为什么区域是个问题

Dreamina 的 API 主机**按账号归属地划分**。把美区账号打到新加坡集群会得到：

```
ret=1015 login error
```

看起来像 sessionid 失效，其实只是打错了地方。这个错误信息极具误导性——
排查时很容易往「账号被封」「cookie 过期」方向跑偏。

归属地由两个 cookie 决定：

| Cookie | 含义 | 示例 |
| --- | --- | --- |
| `store-idc` | 数据中心 | `useast5` / `sg1` / `jp1` |
| `store-country-code` | 国家 | `us` / `vn` / `jp` |

添加账号时管理器会自动从整段 Cookie 里抽这两个值。

---

## 2. 三级解析

解析集群时按这个顺序：

1. **缓存** —— 之前探测成功过的结果（按 `store-idc|country` 缓存）
2. **store-idc 前缀** —— `useast*` → US，`sg*`/`my*` → SG，`jp*` → JP …
3. **国家代码** —— `vn` → SG，`jp` → JP，`gb` → EU …

都没有命中时退回美区，但**会继续自动探测**（见下）。

### 内置的区域映射

| 国家 | 首选集群 |
| --- | --- |
| `us` `ca` `mx` `br` | US |
| `sg` `my` `id` `th` `ph` `**vn**` | SG |
| `jp` `kr` `tw` `hk` | JP |
| `gb` `de` `fr` | EU |

---

## 3. 自动探测：猜不中也没关系

新区域的主机名没法穷举，而且随时可能变。所以系统不依赖「猜对」——
它会把候选集群依次试一遍：

```
首选集群 → 1015 ─→ 下一个候选 → 1015 ─→ 下一个 → 成功
                                              ↓
                                     记住结果，后续直接用
```

**只有 `1015` 才会触发换集群。** 其他错误码（3018 权限不足、参数错误等）
换集群纯属浪费——它们不是「打错地方」造成的。

探测成功的集群按归属地缓存，所以每个区域只需要付出一次探测成本。
缓存是进程内的，重启后重新探测（通常第一次探活就完成了）。

---

## 4. 请求头里的国家 vs URL 里的区域

这两个**必须分开**，混用会让平台看到自相矛盾的归属信号：

```
越南账号，走新加坡集群：
  URL:              ...&region=SG        ← 集群的区域
  loc:              vn                   ← 账号的国家
  store-country-code: vn                 ← 账号的国家
```

早期的实现把 `loc` / `store-country-code` 也写成了集群的 region，
导致越南账号发送 `loc=SG`（而它其实是越南账号）。已修正，有测试锁住。

---

## 5. 时区

浏览器通道会按账号国家设置页面时区：

| 国家 | 时区 |
| --- | --- |
| `us` | America/Los_Angeles |
| `jp` `kr` | Asia/Tokyo / Asia/Seoul |
| `vn` | Asia/Ho_Chi_Minh |
| `sg` `my` `id` `th` `ph` | 各自的东南亚时区 |
| `gb` `de` `fr` | 各自的欧洲时区 |

**为什么在意这个**：账号在日区、代理在日本，浏览器却报美国时间，
是一个完全没必要出现的指纹差异。

实现上，Node sidecar 用 Playwright 的 `timezoneId`；
Electron 桌面端用 CDP 的 `Emulation.setTimezoneOverride`（失败只记日志，不中断）。

---

## 6. 手动补充区域

如果某个区域自动探测也找不到，把主机名写进 `regions.json`
（放数据目录，或由 `MANAGER_REGIONS_FILE` 指定）：

```json
[
  {
    "name": "JP",
    "region": "JP",
    "api": "mweb-api-jp.capcut.com",
    "commerce": "commerce-api-jp.capcut.com"
  }
]
```

自定义条目**优先于内置候选**，所以可以用来纠正猜错的内置定义。

### 怎么知道正确的主机名

在浏览器里登录该账号，F12 → Network，随便点一次生成或者刷新积分，
看请求打到哪个域名。那个就是 `api` 的值；积分请求的域名是 `commerce`。

---

## 7. 代理要对齐

区域搞对了但代理没对齐，风控仍然会警觉。建议：

| 账号归属地 | 代理出口 |
| --- | --- |
| 美区 | 美国 |
| 日区 | 日本 |
| 越南 | 越南或新加坡 |

每个账号可以在界面上单独配代理，管理器会用它建立独立的浏览器上下文。

---

## 8. 排查清单

账号打不开时按顺序看：

1. **日志里的集群名** —— 探活日志会写 `会话 acct-xxx 已建立 {proxy, timezone}`
2. **是不是 1015** —— 是的话先怀疑区域，而不是 cookie
3. **代理出口和 account 归属地是否一致**
4. **`regions.json` 里的定义对不对**（如果配了的话）
5. **`store-idc` / `store-country-code` 是否抽到了** —— 在界面的账号详情里看「区域集群」
